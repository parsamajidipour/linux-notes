# Cron Output, Logging, and Failure Diagnosis

A cron job can fail in at least three very different ways.

The scheduler may never launch it.

The process may start and fail immediately.

The process may run successfully from the operating system's point of view while still failing to achieve the intended application result.

Those cases look similar from the outside because the administrator sees only one symptom:

```text
the job did not do what I expected
```

Good cron troubleshooting begins by separating scheduling, process execution, and application outcome.

A useful mental model is:

```text
schedule match
    ->
cron launches command
    ->
shell/interpreter starts
    ->
program performs work
    ->
program writes stdout/stderr
    ->
program exits with a status
    ->
logs/monitoring preserve evidence
```

Every arrow is a possible failure point.

A reliable production cron job therefore needs more than a correct crontab expression. It needs observable output, meaningful exit status, appropriate logging, safe log retention, and a troubleshooting path that does not depend on guesswork.

This chapter focuses on that operational side of cron.

---

## The first distinction: scheduler failure versus command failure

Suppose this entry exists:

```cron
0 2 * * * /opt/jobs/backup.sh
```

At 02:05 the expected backup file does not exist.

There are several possible explanations:

```text
cron daemon was not running
crontab was not loaded
time expression did not match
job was installed under another user
cron launched the command
shell could not execute the script
script started and failed
script succeeded but wrote output somewhere unexpected
backup destination was unavailable
application returned success despite incomplete work
```

The first diagnostic question should be:

> Did cron attempt to start the job?

That is different from:

> Did the backup succeed?

To investigate the scheduler:

```bash
systemctl status cron
```

or:

```bash
systemctl status crond
```

depending on the distribution.

Then inspect recent scheduler logs:

```bash
journalctl -u cron --since "today"
```

or:

```bash
journalctl -u crond --since "today"
```

Traditional syslog-based systems may use:

```bash
grep CRON /var/log/syslog
```

or:

```bash
grep CROND /var/log/cron
```

If the logs show something like:

```text
CRON[18420]: (alice) CMD (/opt/jobs/backup.sh)
```

then schedule matching worked and cron attempted command execution.

The investigation can move one layer deeper.

If there is no corresponding scheduler event, investigate the crontab itself before debugging the script.

This simple separation prevents hours of debugging code that cron never launched.

---

## Know where cron logs on the target system

There is no universal Linux cron log path.

Possible logging destinations include:

```text
systemd journal
/var/log/syslog
/var/log/cron
/var/log/messages
local mail
application-specific files
```

The exact path depends on:

```text
distribution
cron implementation
syslog daemon
journald forwarding configuration
rsyslog rules
package defaults
```

A Debian or Ubuntu machine may expose cron activity through:

```bash
journalctl -u cron
```

and possibly:

```bash
grep CRON /var/log/syslog
```

An RPM-family system using `crond` may use:

```bash
journalctl -u crond
```

or:

```bash
grep CROND /var/log/cron
```

Do not memorize a single path and assume it applies everywhere.

Discover the service first:

```bash
systemctl list-units --type=service | grep -E 'cron|crond'
```

Then inspect:

```bash
systemctl status cron
```

or:

```bash
systemctl status crond
```

The status output normally reveals the unit name, process ID, recent messages, and whether the daemon is active.

---

## The system journal is often the fastest place to start

For a systemd-based machine:

```bash
journalctl -u cron
```

shows messages associated with the cron service.

Useful time filters include:

```bash
journalctl -u cron --since "10 minutes ago"
journalctl -u cron --since "2026-09-13 02:00:00"
journalctl -u cron --until "2026-09-13 03:00:00"
```

Follow logs live:

```bash
journalctl -fu cron
```

Now create a temporary entry:

```cron
* * * * * /usr/bin/logger -t cron-lab "job executed"
```

In another terminal:

```bash
journalctl -f
```

After the minute changes, you should see both cron's execution event and the message generated by `logger`.

This is a powerful lab because it proves the whole path:

```text
crontab loaded
time matched
cron launched shell
logger executed
journald received application output
```

It does not prove every future application will work, but it validates the scheduling chain.

---

## Scheduler logs do not contain all command output

A common misconception is that:

```bash
journalctl -u cron
```

will automatically contain everything printed by every cron job.

That is not generally true.

Cron logs may show:

```text
which user
which command
when it launched
session open/close events
parser errors
```

but job stdout and stderr are often handled separately.

A job such as:

```cron
* * * * * echo "hello"
```

may cause cron to attempt local mail delivery instead of placing `hello` in the cron daemon's own journal.

Whether that mail is actually delivered depends on local mail configuration.

This is why:

```text
cron log says command ran
but I cannot find the command output
```

is completely possible.

The scheduler log and the application's output channel are different things.

---

## Standard output and standard error are the primary evidence channels

Every normal Unix process begins with file descriptors:

```text
0 = stdin
1 = stdout
2 = stderr
```

A program can write normal results to stdout:

```bash
echo "backup complete"
```

and diagnostics to stderr:

```bash
echo "backup failed" >&2
```

A cron job needs an intentional policy for both streams.

This entry:

```cron
0 2 * * * /opt/jobs/backup.sh
```

leaves output handling to cron's default behavior.

This one redirects both streams into a file:

```cron
0 2 * * * /opt/jobs/backup.sh >> /var/log/backup.log 2>&1
```

This one keeps them separate:

```cron
0 2 * * * /opt/jobs/backup.sh \
    >> /var/log/backup.stdout.log \
    2>> /var/log/backup.stderr.log
```

The best choice depends on the application.

A combined log makes chronological reading easy.

Separate logs make it easier to distinguish informational output from failure output.

For production operations, the important point is not which style is universally correct. The important point is that output should not disappear accidentally.

---

## Why `2>&1` is written after the stdout redirection

This is correct for combining both streams:

```bash
command >> /var/log/task.log 2>&1
```

The shell processes redirections from left to right.

First:

```text
stdout -> /var/log/task.log
```

then:

```text
stderr -> wherever stdout currently points
```

so both go to the log file.

Compare:

```bash
command 2>&1 >> /var/log/task.log
```

Here:

```text
stderr -> current stdout
```

happens first.

Then:

```text
stdout -> file
```

stderr may remain connected to its original destination.

You can demonstrate this safely:

```bash
cat > /tmp/streams.sh <<'EOF'
#!/bin/sh
echo "stdout message"
echo "stderr message" >&2
EOF

chmod +x /tmp/streams.sh
```

Run:

```bash
/tmp/streams.sh > /tmp/a.log 2>&1
```

Then:

```bash
cat /tmp/a.log
```

Expected:

```text
stdout message
stderr message
```

Now:

```bash
/tmp/streams.sh 2>&1 > /tmp/b.log
```

Depending on the terminal and surrounding shell, `stderr message` can appear on screen while only stdout lands in the file.

Understanding file-descriptor duplication is important because cron makes otherwise invisible stderr particularly easy to lose.

---

## Append versus overwrite

This:

```cron
* * * * * /opt/jobs/check.sh > /var/log/check.log 2>&1
```

overwrites the file every minute.

Only the most recent execution remains.

This:

```cron
* * * * * /opt/jobs/check.sh >> /var/log/check.log 2>&1
```

appends.

That preserves history, but introduces another problem: unbounded growth.

A job that writes 200 KB per minute produces approximately:

```text
200 KB * 60 * 24
```

per day.

That is:

```text
288 MB/day
```

Approximately:

```text
8.6 GB/month
```

for one noisy cron job.

Logging is useful only if retention is controlled.

---

## A cron job can fill the root filesystem

Consider:

```cron
* * * * * /opt/app/worker --verbose >> /var/log/worker-cron.log 2>&1
```

If the application emits large output continuously and nothing rotates the file, disk usage grows indefinitely.

Inspect:

```bash
du -h /var/log/worker-cron.log
```

and:

```bash
df -h /
```

A full root filesystem can cause failures far beyond cron:

```text
database writes fail
package manager fails
services cannot create temporary files
journald cannot persist logs
applications crash
SSH sessions behave unexpectedly
```

Therefore log retention is part of job reliability.

A production cron job should answer:

```text
Where is output stored?
How large can it become?
Who rotates it?
How long is it retained?
Is compression enabled?
What happens if disk space is low?
```

## Use logrotate for file-based cron logs

Suppose cron writes:

```text
/var/log/company-backup.log
```

Create:

```text
/etc/logrotate.d/company-backup
```

with content such as:

```text
/var/log/company-backup.log {
    daily
    rotate 14
    compress
    missingok
    notifempty
    create 0640 root adm
}
```

This means conceptually:

```text
check daily
retain 14 rotated copies
compress older logs
ignore missing file
skip empty logs
recreate with controlled permissions
```

Test syntax:

```bash
logrotate -d /etc/logrotate.conf
```

The `-d` mode is useful for debugging because it does not actually rotate files.

Force rotation only when you understand the effect:

```bash
sudo logrotate -f /etc/logrotate.d/company-backup
```

Then inspect:

```bash
ls -lh /var/log/company-backup*
```

A cron job that produces persistent file logs should usually have a retention plan from the beginning.

---

## `copytruncate` is not automatically safe

Some logrotate configurations use:

```text
copytruncate
```

This copies the log and truncates the original file without asking the process to reopen it.

It is convenient for long-running processes that keep a file descriptor open.

But a typical cron command opens the log file anew on every invocation because the shell performs:

```bash
>> /var/log/job.log
```

each time.

That means `copytruncate` may be unnecessary.

It also has a small race window during copying and truncation where log data can be lost or duplicated.

For cron-generated logs, normal rename/create rotation is often simpler.

Understand the writer before choosing rotation semantics.

---

## The `logger` command integrates cron jobs with syslog/journald

Instead of managing a dedicated file, a script can write to the system logging stack.

Example:

```bash
logger -t nightly-backup "backup started"
```

Inspect:

```bash
journalctl -t nightly-backup
```

A script:

```bash
#!/bin/sh
set -eu

TAG=nightly-backup

/usr/bin/logger -t "$TAG" "starting"

if /usr/local/libexec/backup; then
    /usr/bin/logger -t "$TAG" "completed successfully"
else
    rc=$?
    /usr/bin/logger -p user.err -t "$TAG" \
        "failed rc=$rc"
    exit "$rc"
fi
```

Now operations can query:

```bash
journalctl -t nightly-backup --since "7 days ago"
```

This has several advantages:

```text
centralized timestamps
journal retention policies
priority metadata
easy filtering
integration with existing log forwarding
```

For many servers, structured system logging is cleaner than creating one file per cron job.

---

## Use logging priority meaningfully

`logger` can assign priorities.

Example:

```bash
logger -p user.info -t backup "backup started"
logger -p user.warning -t backup "backup slower than expected"
logger -p user.err -t backup "backup failed"
```

Inspect only errors:

```bash
journalctl -t backup -p err
```

The standard syslog severity levels include:

```text
emerg
alert
crit
err
warning
notice
info
debug
```

Do not mark every message as an error.

If all messages are critical, none are operationally meaningful.

A good scheduled task may log:

```text
info     normal start/completion
warning  recoverable anomaly
err      failed execution
crit     severe integrity or availability risk
```

Severity becomes especially useful when logs are forwarded to monitoring or SIEM systems.

---

## Application logs are often more valuable than cron logs

Suppose cron launches:

```cron
* * * * * /usr/bin/php /srv/app/artisan schedule:run
```

Cron can prove that PHP was started.

It cannot explain why a Laravel scheduled command later failed due to:

```text
database deadlock
HTTP 500
queue timeout
application validation
business-rule exception
```

Those details belong in application logs.

Similarly:

```cron
*/10 * * * * /opt/api/.venv/bin/python /opt/api/sync.py
```

may require Python application logs with stack traces.

A mature diagnostic model uses several layers:

```text
cron scheduler log
shell stderr
application log
database log
remote-service log
monitoring alert
```

Do not force all observability into the cron daemon.

Cron is the launcher, not the application debugger.

---

## Exit status is essential evidence

After a command finishes, the kernel makes its exit status available to the parent process.

Conventionally:

```text
0 = success
non-zero = failure or special condition
```

Manually:

```bash
/opt/jobs/task.sh
echo $?
```

Example:

```text
2
```

That value often carries more operational meaning than output text.

A script should preserve failure status.

Bad:

```bash
#!/bin/sh

/usr/local/bin/backup
echo "backup process finished"
```

If `backup` returns `7` but `echo` returns `0`, the script's exit status becomes `0`.

Better:

```bash
#!/bin/sh

/usr/local/bin/backup
rc=$?

echo "backup process finished rc=$rc"
exit "$rc"
```

or:

```bash
#!/bin/sh
set -e

/usr/local/bin/backup
echo "backup process finished"
```

when `set -e` semantics are appropriate and understood.

Monitoring systems need a machine-readable result.

---

## Cron itself may not retain the child's exit status in an obvious place

Traditional cron usually launches the command and handles output, but it does not necessarily create a durable database of:

```text
job name
start time
finish time
exit code
duration
```

This is a major operational limitation compared with more feature-rich schedulers.

If exit history matters, record it explicitly.

Example wrapper:

```bash
#!/usr/bin/env bash
set -u

JOB=nightly-backup
START=$(date +%s)

logger -t "$JOB" "started"

if /usr/local/libexec/backup; then
    rc=0
else
    rc=$?
fi

END=$(date +%s)
DURATION=$((END - START))

logger -t "$JOB" \
    "finished rc=$rc duration_seconds=$DURATION"

exit "$rc"
```

Now:

```bash
journalctl -t nightly-backup
```

contains enough information to reconstruct basic execution history.

---

## Duration is a valuable metric

A job can still succeed while becoming unhealthy.

Suppose a database backup usually takes:

```text
8 minutes
```

and over several weeks grows to:

```text
12 minutes
20 minutes
38 minutes
55 minutes
```

The exit status remains `0`, but soon a daily backup may overlap another maintenance task.

Recording duration reveals degradation before outright failure.

A shell wrapper:

```bash
#!/bin/sh

start=$(/usr/bin/date +%s)

/usr/local/bin/report
rc=$?

end=$(/usr/bin/date +%s)
duration=$((end - start))

/usr/bin/logger -t report-job \
    "rc=$rc duration_seconds=$duration"

exit "$rc"
```

For higher-resolution timing:

```bash
/usr/bin/time -p /usr/local/bin/report
```

produces:

```text
real 12.34
user 3.10
sys 1.08
```

Be aware that `time` may be both a shell keyword and an external program. Use the intended one explicitly when scripting.

---

## Distinguish "started" from "completed"

A single log line:

```text
backup started
```

is not evidence of completion.

A robust job records both boundaries:

```text
job_id=backup date=... event=start
job_id=backup date=... event=finish rc=0 duration=...
```

Example:

```bash
#!/usr/bin/env bash
set -u

JOB=backup
RUN_ID="$(date -u +%Y%m%dT%H%M%SZ)-$$"
START="$(date +%s)"

logger -t "$JOB" \
    "run_id=$RUN_ID event=start"

run_backup
rc=$?

END="$(date +%s)"

logger -t "$JOB" \
    "run_id=$RUN_ID event=finish rc=$rc duration=$((END-START))"

exit "$rc"
```

The run identifier helps correlate messages from the same execution if overlapping jobs occur.

---

## Add timestamps to file logs

This cron line:

```cron
* * * * * /opt/jobs/task.sh >> /var/log/task.log 2>&1
```

does not automatically prefix every output line with a timestamp.

If the script writes:

```text
connected
processed 143 records
done
```

you may not know which minute produced each line.

One approach is for the script to log with timestamps:

```bash
log() {
    printf '%s %s\n' "$(date -Is)" "$*"
}

log "starting"
```

Another approach is to use system logging:

```bash
logger -t task "starting"
```

which provides timestamp metadata externally.

Avoid complex line-prefix pipelines unless necessary, because they can interfere with buffering and exit-status handling.

For example:

```bash
command | while read -r line; do
    printf '%s %s\n' "$(date -Is)" "$line"
done
```

adds timestamps but introduces a pipeline whose failure semantics require care.

Application-native structured logging is usually better.

---

## Redirecting output to `/dev/null` should be deliberate

Administrators often write:

```cron
* * * * * /opt/jobs/task.sh >/dev/null 2>&1
```

because they do not want mail or noisy logs.

This discards all evidence.

If the job later fails, there may be nothing to diagnose.

Suppressing known harmless output is reasonable only when failure is observed elsewhere.

For example:

```cron
* * * * * /opt/jobs/heartbeat.sh >/dev/null 2>&1
```

can be acceptable if the heartbeat itself reports success or failure to an external monitoring system.

But this:

```cron
0 2 * * * /opt/jobs/database-backup >/dev/null 2>&1
```

with no other monitoring is operationally weak.

A better model is:

```text
normal success is quiet
errors are preserved
failure triggers monitoring
```

A script can write nothing on success and meaningful diagnostics on stderr.

Then cron mail, journald, or an alert wrapper can capture only anomalies.

---

## Cron mail is useful but should not be assumed

Traditional cron behavior often mails job output to the user or to `MAILTO`.

Example:

```cron
MAILTO=ops@example.com

0 2 * * * /opt/jobs/backup.sh
```

If the script writes:

```text
backup failed
```

cron may pass the output to a local mail transport.

But several things can break this model:

```text
no local MTA installed
MTA not configured
DNS problems
mail rejected externally
spam filtering
MAILTO empty
mail queue stuck
local-only delivery
```

Check whether a mail system exists:

```bash
command -v sendmail
command -v mail
systemctl status postfix 2>/dev/null
systemctl status exim4 2>/dev/null
```

Check queues using implementation-specific commands, for example:

```bash
mailq
```

Do not conclude:

```text
no email arrived, therefore cron did not run
```

Mail delivery and cron execution are independent systems.

---

## Test mail behavior explicitly

Create a controlled job:

```cron
MAILTO=your-test-address@example.com

* * * * * echo "cron mail test $(date)"
```

If no message arrives, inspect:

```text
cron logs
mail service logs
mail queue
local mailbox
```

On systems with local user mail:

```bash
mail
```

or files under:

```text
/var/mail/
```

may contain cron messages.

A local cron mail message can be technically delivered even though nothing reached an external inbox.

Treat local mail delivery as a separate subsystem.

---

## `MAILTO=""` can intentionally suppress cron mail

On cron implementations supporting it:

```cron
MAILTO=""
```

disables mail for the relevant entries.

This can be useful when logs are handled elsewhere.

For example:

```cron
MAILTO=""

0 2 * * * /opt/jobs/backup >> /var/log/backup.log 2>&1
```

But now log rotation and monitoring become even more important.

Suppressing one output channel increases dependence on the remaining channels.

## A command can fail before your script starts

Suppose cron logs:

```text
CMD (/opt/jobs/report.sh)
```

but the script's own "started" message never appears.

Possible causes include:

```text
file does not exist
permission denied
bad shebang
interpreter missing
CRLF in shebang
filesystem mounted noexec
parent directory not traversable
dynamic loader failure
```

Test:

```bash
ls -l /opt/jobs/report.sh
file /opt/jobs/report.sh
head -n 1 /opt/jobs/report.sh
namei -l /opt/jobs/report.sh
```

Execute as the exact user:

```bash
sudo -u reportuser /opt/jobs/report.sh
```

For a script:

```bash
strace -f -e execve sudo -u reportuser /opt/jobs/report.sh
```

can reveal interpreter execution attempts.

An error such as:

```text
bad interpreter: No such file or directory
```

may mean the script exists but its shebang interpreter does not.

Example:

```bash
#!/usr/bin/bash
```

on a system where Bash is:

```text
/bin/bash
```

or:

```bash
#!/bin/sh^M
```

because of Windows line endings.

Cron cannot repair an invalid executable.

---

## Capture stderr during diagnosis

A terrible troubleshooting entry is:

```cron
* * * * * /opt/jobs/report.sh >/dev/null 2>&1
```

because it suppresses the evidence you need.

During diagnosis, change temporarily to:

```cron
* * * * * /opt/jobs/report.sh >> /tmp/report-cron-debug.log 2>&1
```

Then:

```bash
tail -f /tmp/report-cron-debug.log
```

Use `/tmp` only for short-lived diagnostics and avoid putting sensitive production data there.

For real deployment:

```text
/var/log/application/
journald
central logging
```

is better.

Once the issue is understood, replace temporary debugging with a deliberate long-term logging design.

---

## A failing job may leave no output at all

Some programs fail silently and return only an exit code.

Example:

```bash
/usr/local/bin/tool --quiet
echo $?
```

returns:

```text
4
```

but prints nothing.

If cron's only observation mechanism is output mail, this failure could go unnoticed.

Wrap it:

```bash
#!/bin/sh

/usr/local/bin/tool --quiet
rc=$?

if [ "$rc" -ne 0 ]; then
    echo "tool failed rc=$rc" >&2
fi

exit "$rc"
```

Now the failure produces both:

```text
non-zero status
diagnostic stderr
```

Those two signals together are much more observable.

---

## A successful exit code can still represent business failure

Consider:

```bash
curl https://api.example.com/export > /var/backups/export.json
```

By default, `curl` can successfully complete the HTTP transfer even if the server returns an HTTP error response, depending on options and failure mode.

A file may contain:

```json
{"error":"unauthorized"}
```

while the shell sees exit status `0`.

A stronger command:

```bash
curl --fail --show-error --silent \
    https://api.example.com/export \
    > /var/backups/export.json
```

makes HTTP error responses fail the command.

Similarly, a database query can return syntactically valid but incomplete results.

A backup file can exist but be empty.

A synchronization script can copy zero files when thousands were expected.

Monitoring cron only at the process level is insufficient for critical jobs.

Validate outcomes.

Example:

```bash
#!/bin/sh
set -eu

tmp=$(/usr/bin/mktemp)
trap 'rm -f "$tmp"' EXIT

/usr/bin/curl \
    --fail \
    --show-error \
    --silent \
    https://api.example.com/export \
    > "$tmp"

size=$(/usr/bin/stat -c %s "$tmp")

if [ "$size" -lt 1000 ]; then
    echo "export unexpectedly small: ${size} bytes" >&2
    exit 20
fi

/bin/mv "$tmp" /var/backups/export.json
```

A meaningful cron check tests the intended result, not just process creation.

---

## Validate backup artifacts

Suppose a job creates:

```text
/var/backups/app.tar.gz
```

A simple existence check:

```bash
test -f /var/backups/app.tar.gz
```

is weak.

A zero-byte file exists too.

Add:

```bash
test -s /var/backups/app.tar.gz
```

which requires a non-empty regular file.

For a gzip archive:

```bash
gzip -t /var/backups/app.tar.gz
```

For a tar archive:

```bash
tar -tzf /var/backups/app.tar.gz >/dev/null
```

For database dumps, validate format or perform periodic restore tests.

A backup pipeline that logs:

```text
backup completed successfully
```

without verifying restorability can produce false confidence.

Cron reliability is ultimately about the outcome being correct.

---

## Pipeline failures are a common source of false success

Consider:

```cron
0 2 * * * /usr/local/bin/export-db | gzip > /var/backups/db.gz
```

If `export-db` fails but `gzip` exits successfully after compressing partial input, a shell without `pipefail` may report the pipeline as successful.

A Bash wrapper:

```bash
#!/usr/bin/env bash
set -o pipefail

/usr/local/bin/export-db \
    | /usr/bin/gzip \
    > /var/backups/db.gz
```

Now:

```bash
echo $?
```

reflects failure from any pipeline component.

For stronger safety, write to a temporary file:

```bash
#!/usr/bin/env bash
set -euo pipefail

tmp=$(/usr/bin/mktemp /var/backups/.db.XXXXXX.gz)
trap 'rm -f "$tmp"' EXIT

/usr/local/bin/export-db \
    | /usr/bin/gzip \
    > "$tmp"

/usr/bin/gzip -t "$tmp"

/bin/mv "$tmp" /var/backups/db.gz

trap - EXIT
```

This prevents a failed run from replacing the last known-good backup with a partial file.

Logging and failure handling are deeply connected.

---

## `set -e` is helpful but not magic

A script:

```bash
#!/bin/sh
set -e

command-a
command-b
command-c
```

normally stops when a simple command fails.

That is useful for cron jobs because failure does not silently cascade into later steps.

But `set -e` has subtle rules involving:

```text
conditionals
pipelines
logical AND/OR
subshells
command substitutions
functions
```

Do not assume it turns shell into exception-safe code.

This:

```bash
if grep pattern file; then
    echo found
fi
```

does not cause the script to exit merely because `grep` returns `1` inside the conditional.

Likewise:

```bash
command-a || echo "ignored"
```

explicitly handles failure.

Use `set -e` as one tool, but still design critical error paths intentionally.

Bash jobs often use:

```bash
set -euo pipefail
```

which combines:

```text
-e  exit on many unhandled failures
-u  treat unset variables as errors
-o pipefail  propagate pipeline failures
```

This is useful when understood.

---

## Traps can record unexpected failures

Bash provides an `ERR` trap.

Example:

```bash
#!/usr/bin/env bash
set -Eeuo pipefail

trap 'rc=$?; logger -p user.err -t report-job \
    "failed rc=$rc line=$LINENO command=$BASH_COMMAND"; exit "$rc"' ERR

cd /srv/reporting
/opt/reporting/.venv/bin/python daily.py
```

This can create useful failure context.

But do not put secrets into commands if shell tracing or error reporting logs `$BASH_COMMAND`.

For example:

```bash
curl -H "Authorization: Bearer $TOKEN" ...
```

could expose the token in diagnostics.

A more secure script keeps secrets in protected files or passes them through mechanisms that do not appear in log messages.

Debuggability and confidentiality must be balanced.

---

## `tee` is useful but changes pipeline semantics

During debugging, administrators often want output both on screen and in a file:

```bash
command 2>&1 | tee /tmp/debug.log
```

This is convenient.

But without Bash `pipefail`, the pipeline's exit code may be `tee`'s status, not the command's.

Use:

```bash
set -o pipefail
command 2>&1 | tee /tmp/debug.log
```

Then inspect:

```bash
echo $?
```

For a cron wrapper:

```bash
#!/usr/bin/env bash
set -o pipefail

/opt/jobs/task 2>&1 \
    | /usr/bin/tee -a /var/log/task.log
```

Now command failure can propagate.

Every logging pipeline should be reviewed for whether it accidentally masks the exit code.

## Buffering can make a running job look dead

Programs may buffer stdout when it is redirected to a file rather than attached to a terminal.

Suppose:

```python
import time

for i in range(100):
    print(i)
    time.sleep(10)
```

Cron:

```cron
* * * * * /usr/bin/python3 /opt/jobs/progress.py >> /var/log/progress.log 2>&1
```

The log may update less frequently than expected due to buffering.

Run Python unbuffered:

```cron
* * * * * /usr/bin/python3 -u /opt/jobs/progress.py >> /var/log/progress.log 2>&1
```

or:

```cron
PYTHONUNBUFFERED=1

* * * * * /usr/bin/python3 /opt/jobs/progress.py >> /var/log/progress.log 2>&1
```

For other commands, tools such as:

```bash
stdbuf
```

can sometimes alter buffering:

```bash
stdbuf -oL -eL command
```

but buffering behavior depends on the program and language runtime.

Before concluding that cron is stalled, check whether the process is actually alive:

```bash
pgrep -af progress.py
```

and whether it is consuming resources:

```bash
ps -o pid,etimes,pcpu,pmem,cmd -p PID
```

## Process inspection is essential during live failures

If a cron job appears stuck:

```bash
pgrep -af backup
```

Then:

```bash
ps -o \
    pid,ppid,user,stat,etime,pcpu,pmem,wchan:30,cmd \
    -p PID
```

Important fields:

```text
STAT   process state
ETIME  elapsed runtime
%CPU   CPU usage
%MEM   memory usage
WCHAN  kernel wait location
```

A process in:

```text
D
```

state may be waiting on uninterruptible I/O.

A process in:

```text
S
```

may be sleeping or waiting normally.

Inspect open files:

```bash
sudo lsof -p PID
```

Inspect network sockets:

```bash
sudo ss -tpn
```

Inspect process tree:

```bash
pstree -ap PID
```

The cron scheduler may be functioning perfectly while the child is blocked on storage, DNS, network, database locks, or another external dependency.

## Use `/proc` to inspect the exact runtime context

For a running process:

```bash
cat /proc/PID/status
```

shows identity and process state.

Inspect environment:

```bash
sudo tr '\0' '\n' < /proc/PID/environ
```

Be careful: environment variables may contain secrets.

Inspect current directory:

```bash
readlink /proc/PID/cwd
```

Inspect executable:

```bash
readlink /proc/PID/exe
```

Inspect file descriptors:

```bash
ls -l /proc/PID/fd
```

Inspect command line:

```bash
tr '\0' ' ' < /proc/PID/cmdline
echo
```

This is extremely useful when the question is:

```text
What did cron actually run?
```

The live process is stronger evidence than assumptions about configuration.

## `strace` can identify system-call level failures

Suppose a job fails with only:

```text
could not open configuration
```

Trace file activity:

```bash
strace -f -e trace=file \
    sudo -u appuser \
    /opt/app/bin/task
```

You may see:

```text
openat(..., "/home/appuser/.config/app.conf", ...) = -1 ENOENT
```

Now the problem is concrete.

For network investigation:

```bash
strace -f -e trace=network \
    sudo -u appuser \
    /opt/app/bin/task
```

For process execution:

```bash
strace -f -e execve \
    sudo -u appuser \
    /opt/app/bin/task
```

Example:

```text
execve("/usr/bin/python3", ...)
execve("/usr/bin/curl", ...)
```

A missing binary may appear as repeated:

```text
ENOENT
```

during `PATH` search.

`strace` is especially useful when scripts call external programs and the textual error is vague.

## Do not run enormous traces blindly in production

This is technically possible:

```bash
strace -f -o /tmp/full.trace command
```

but high-volume applications can generate enormous traces and incur overhead.

Target the problem.

Examples:

```bash
strace -f -e execve ...
strace -f -e openat ...
strace -f -e connect ...
strace -f -e trace=file ...
```

Attach to a stuck process:

```bash
sudo strace -p PID
```

or selected calls:

```bash
sudo strace -p PID -e trace=network
```

Use short observation windows and protect trace files because they can contain filenames, paths, arguments, and potentially sensitive data.

## Timeouts prevent cron jobs from hanging forever

Suppose:

```cron
*/5 * * * * /opt/jobs/check-remote-api
```

occasionally hangs because a network call has no timeout.

After an hour, many overlapping copies may exist.

Use application-native timeouts where possible.

For `curl`:

```bash
curl \
    --connect-timeout 5 \
    --max-time 30 \
    https://api.example.com/health
```

A generic outer limit can use:

```bash
timeout 5m /opt/jobs/check-remote-api
```

Cron:

```cron
*/5 * * * * /usr/bin/timeout 4m /opt/jobs/check-remote-api
```

Now the job cannot normally outlive its interval.

`timeout` returns specific exit codes for timeout-related conditions, so the wrapper can log them.

Example:

```bash
/usr/bin/timeout 4m /opt/jobs/check-remote-api
rc=$?

case "$rc" in
    0)
        ;;
    124)
        echo "job timed out" >&2
        ;;
    *)
        echo "job failed rc=$rc" >&2
        ;;
esac

exit "$rc"
```

Timeouts are a reliability tool, not a substitute for understanding why a process hangs.

## DNS failures often masquerade as cron problems

A networked job:

```bash
curl https://service.internal
```

may work manually and fail at night.

Possible causes include:

```text
DNS resolver unavailable
VPN only active in interactive session
split DNS
network interface state
container DNS differences
temporary resolver timeout
```

Check:

```bash
getent hosts service.internal
```

as the job user.

Use:

```bash

```

where systemd-resolved is present.

Inspect:

```bash
cat /etc/resolv.conf
```

A cron log that says:

```text
Could not resolve host
```

is a network-resolution problem, not a cron parser problem.

Operational diagnosis becomes faster when error messages are classified by subsystem.

## Use unique run IDs for complex jobs

When executions can overlap or when logs are centralized, a run identifier makes correlation easier.

Example:

```bash
RUN_ID="$(date -u +%Y%m%dT%H%M%SZ)-$$"
```

Then:

```bash
logger -t sync-job \
    "run_id=$RUN_ID event=start"

logger -t sync-job \
    "run_id=$RUN_ID event=batch_complete batch=4 records=821"

logger -t sync-job \
    "run_id=$RUN_ID event=finish rc=0"
```

Now:

```bash
journalctl -t sync-job | grep "run_id=$RUN_ID"
```

extracts one execution.

For distributed systems, a UUID may be better:

```bash
uuidgen
```

or an application-generated identifier.

Logs become much more useful when one run can be reconstructed precisely.

## Structured logs improve machine analysis

Human-readable:

```text
backup completed successfully in 38 seconds
```

is fine.

Structured:

```text
event=finish job=backup rc=0 duration_seconds=38 files=1824 bytes=914220881
```

is easier to parse.

JSON is another option:

```json
{
  "event": "finish",
  "job": "backup",
  "rc": 0,
  "duration_seconds": 38,
  "files": 1824
}
```

If using JSON, let the application generate valid JSON rather than building it unsafely with shell string concatenation.

Structured data helps:

```text
central log search
dashboards
alerts
long-term trend analysis
automatic incident correlation
```

Cron itself is simple, but the processes it launches can participate in modern observability systems.

## Record meaningful counters, not just "success"

A synchronization job can log:

```text
rc=0
```

and still have processed no data.

Useful domain-specific metrics might include:

```text
rows_exported
files_uploaded
bytes_transferred
records_failed
records_skipped
backup_size
old_files_deleted
API_pages_processed
```

Example:

```text
event=finish rc=0 records_read=10542 records_written=10542 errors=0
```

Now monitoring can alert on:

```text
records_written = 0
```

even though exit status is zero.

The distinction is important:

```text
process success
business success
```

are not always the same thing.

## A production backup wrapper

A more complete example:

```bash
#!/usr/bin/env bash
set -Eeuo pipefail

JOB=app-backup
BACKUP_DIR=/var/backups/app
RUN_ID="$(date -u +%Y%m%dT%H%M%SZ)-$$"
START="$(date +%s)"
TMP=""

cleanup() {
    if [[ -n "${TMP:-}" && -e "$TMP" ]]; then
        rm -f -- "$TMP"
    fi
}

fail() {
    rc=$?
    end=$(date +%s)

    logger -p user.err -t "$JOB" \
        "run_id=$RUN_ID event=fail rc=$rc duration_seconds=$((end-START))"

    cleanup
    exit "$rc"
}

trap fail ERR
trap cleanup EXIT

mkdir -p "$BACKUP_DIR"

TMP="$(mktemp "$BACKUP_DIR/.app-backup.XXXXXX.tar.gz")"

logger -t "$JOB" \
    "run_id=$RUN_ID event=start"

tar -czf "$TMP" \
    -C /srv/app \
    data uploads

gzip -t "$TMP"

size=$(stat -c %s "$TMP")

if (( size < 1024 )); then
    echo "backup unexpectedly small: $size bytes" >&2
    exit 30
fi

FINAL="$BACKUP_DIR/app-$(date -u +%F).tar.gz"

mv "$TMP" "$FINAL"
TMP=""

END="$(date +%s)"

logger -t "$JOB" \
    "run_id=$RUN_ID event=finish rc=0 duration_seconds=$((END-START)) bytes=$size file=$FINAL"
```

Cron:

```cron
15 2 * * * /usr/local/sbin/app-backup
```

This wrapper provides:

```text
unique run identity
start event
failure event
duration
temporary-file cleanup
archive validation
size validation
atomic final rename
meaningful exit status
structured log metadata
```

That is much stronger than:

```cron
15 2 * * * tar -czf /var/backups/app.tar.gz /srv/app
```

even though both appear to perform the same basic task.

## The failure handler must preserve the original error

Error handlers can accidentally replace the real exit code.

Bad:

```bash
command
if [ "$?" -ne 0 ]; then
    logger "failed"
    exit 1
fi
```

This throws away the original status.

If the command returns:

```text
28
```

the wrapper always returns:

```text
1
```

That may lose useful diagnostic meaning.

Better:

```bash
command
rc=$?

if [ "$rc" -ne 0 ]; then
    logger "failed rc=$rc"
    exit "$rc"
fi
```

Similarly, if a cleanup command fails after the main command succeeds, decide intentionally which status matters.

A scheduled job should define error precedence rather than accidentally inheriting the last shell command's status.

---

## Beware of command substitutions hiding errors

Consider:

```bash
result="$(some-command)"
echo "$result"
```

Under some shell/error-handling combinations, failure semantics may not be as obvious as expected.

A clearer pattern for critical commands:

```bash
if ! result="$(some-command)"; then
    rc=$?
    ...
fi
```

But logical negation again affects `$?`.

Safer:

```bash
result="$(some-command)"
rc=$?

if [ "$rc" -ne 0 ]; then
    echo "some-command failed rc=$rc" >&2
    exit "$rc"
fi
```

In Bash with strict mode, behavior should still be tested in context.

Cron magnifies shell mistakes because nobody is watching the command interactively.

## Validate configuration before the scheduled window

A job should be able to run a preflight test.

Example:

```bash
/opt/jobs/backup --check
```

could validate:

```text
configuration readable
destination mounted
credentials usable
required binaries installed
enough disk space
remote endpoint reachable
database connection available
```

Then deployment can run:

```bash
sudo -u backup /opt/jobs/backup --check
```

without performing the backup.

This is especially useful for long-interval jobs such as monthly maintenance. Waiting a month to discover a missing binary is poor operational design.

## Disk space should be checked where it matters

A backup script may check:

```bash
df -h /
```

while the destination is:

```text
/mnt/backups
```

The correct filesystem is:

```bash
df -h /mnt/backups
```

For machine-readable values:

```bash
df -Pk /mnt/backups
```

or:

```bash
df --output=avail -B1 /mnt/backups
```

Example:

```bash
available=$(
    df --output=avail -B1 /mnt/backups \
    | tail -n 1 \
    | tr -d ' '
)

required=10737418240

if [ "$available" -lt "$required" ]; then
    echo "insufficient backup space" >&2
    exit 40
fi
```

A job can fail before writing partial data if resource checks occur early.

## Check inode exhaustion too

A filesystem can have free bytes but no free inodes.

Inspect:

```bash
df -i /var
```

A job creating millions of small files can encounter:

```text
No space left on device
```

even though:

```bash
df -h
```

shows substantial free capacity.

For jobs that generate many files, both metrics matter:

```bash
df -h DESTINATION
df -i DESTINATION
```

This is a good example of why raw error messages should be preserved. Without stderr, an inode failure can look like a mysterious cron malfunction.

## Observe memory-related failures

A process terminated by the kernel's OOM killer may leave confusing symptoms.

Search kernel logs:

```bash
journalctl -k | grep -i -E 'oom|out of memory|killed process'
```

or:

```bash
dmesg | grep -i -E 'oom|out of memory|killed process'
```

A cron job that disappears midway through processing may have been killed because of memory pressure.

Check:

```bash
free -h
```

and historical monitoring if available.

The scheduler may have started the process correctly.

The kernel may later terminate it.

Again, diagnostics must follow the execution chain beyond cron.

## Signals can explain interrupted jobs

Processes can terminate because they receive signals.

Common examples:

```text
SIGTERM
SIGKILL
SIGHUP
SIGINT
SIGPIPE
```

A shell may report an exit status derived from the signal.

For many shells:

```text
128 + signal number
```

is used.

For example, SIGTERM is signal 15:

```text
143
```

SIGKILL is signal 9:

```text
137
```

These values are clues, not absolute cross-platform guarantees.

If a job ends with `137`, investigate:

```text
manual kill
OOM killer
container memory limit
supervisor action
timeout wrapper
```

If it ends with `143`, investigate:

```text
service shutdown
timeout
administrator termination
deployment
```

Exit status can point toward the subsystem responsible for termination.

## `timeout` may send signals in stages

GNU `timeout` can first send a termination signal and optionally later send `SIGKILL`.

Example:

```bash
timeout --kill-after=30s 5m /opt/jobs/sync
```

Conceptually:

```text
after 5 minutes -> request termination
after another 30 seconds -> force kill if still alive
```

For a job that needs cleanup, install signal handlers.

Bash example:

```bash
#!/usr/bin/env bash
set -euo pipefail

cleanup() {
    rm -f /run/myjob.temp
}

trap cleanup EXIT TERM INT

do_work
```

Be careful: shell traps and child-process signal propagation can become complex. For critical long-running tasks, test shutdown behavior explicitly.

## Diagnose permission failures by testing as the real user

A root administrator may run:

```bash
/opt/jobs/report
```

successfully.

Cron runs it as:

```text
reportuser
```

and fails.

Do not test only as root.

Run:

```bash
sudo -u reportuser /opt/jobs/report
```

Then test dependencies:

```bash
sudo -u reportuser test -r /etc/report/config
sudo -u reportuser test -w /var/lib/report
sudo -u reportuser test -x /opt/jobs/report
```

Check full path:

```bash
namei -l /opt/jobs/report
```

Check ACLs:

```bash
getfacl /var/lib/report
```

Check SELinux where enabled:

```bash
getenforce
ls -Z /opt/jobs/report /var/lib/report
```

Check AppArmor where relevant:

```bash
aa-status
```

A filesystem mode can look correct while a mandatory access-control policy blocks the operation.

## SELinux denials can look like ordinary permission errors

On SELinux-enabled systems, a cron-launched process may receive:

```text
Permission denied
```

even when Unix owner/group/mode bits appear correct.

Inspect:

```bash
getenforce
```

If:

```text
Enforcing
```

search audit messages:

```bash
ausearch -m AVC -ts recent
```

or:

```bash
journalctl | grep -i avc
```

Use SELinux diagnostic tools available on the distribution.

Do not reflexively disable SELinux.

The correct solution is to understand:

```text
source context
target context
requested permission
expected policy
```

A cron failure can expose a legitimate MAC policy violation.

## AppArmor can also block scheduled jobs

On Ubuntu systems:

```bash
aa-status
```

shows loaded profiles.

Kernel or journal messages may contain:

```text
apparmor="DENIED"
```

Search:

```bash
journalctl -k | grep -i apparmor
```

If a scheduled executable works under one invocation path but not another, profile attachment and execution transitions may matter.

Again, the solution is not:

```text
disable security because cron fails
```

The solution is to understand the security context in which the scheduled process executes.

## Diagnose missing files with `namei`, `stat`, and `readlink`

Suppose the log says:

```text
No such file or directory
```

for:

```text
/opt/current/bin/report
```

but:

```bash
ls /opt/current/bin/report
```

shows the file.

Check symlinks:

```bash
readlink -f /opt/current/bin/report
```

Check every path component:

```bash
namei -l /opt/current/bin/report
```

Check metadata:


The missing object may be:

```text
the interpreter from the shebang
a symlink target
a dynamically linked library
a configuration file
the current working directory dependency
```

## Dynamic loader failures can be surprising

A compiled executable can exist but fail because its dynamic linker or a required library is unavailable.

Inspect:

```bash
file /usr/local/bin/tool
```

and:

```bash
ldd /usr/local/bin/tool
```

Potential output:

```text
libexample.so.1 => not found
```

An interactive shell may set:

```text
LD_LIBRARY_PATH
```

while cron does not.

The correct production fix is generally to install libraries into a proper loader path or configure the runtime loader intentionally, not to depend on a developer's shell variable.

Check:

```bash
ldconfig -p | grep example
```

when using glibc-based systems.

A binary startup failure may happen before the application can produce its own logs.

## File timestamps can reveal whether a job ran

Suppose a job should update:

```text

```

Inspect:

```bash

```

Look at:


## `find` can locate recently modified job artifacts

For files changed in the last ten minutes:

```bash
find /var/lib/app \
    -type f \
    -mmin -10 \
    -ls
```

For backups created in the last day:

```bash
find /var/backups/app \
    -type f \
    -mtime -1 \
    -ls
```

Remember that:

```text
-mtime
-mmin
-ctime
```

have different semantics.

`mtime` tracks file content modification.

`ctime` tracks inode metadata changes and is not creation time.

Cron diagnostics benefit from correct filesystem terminology.

## Log the command version when version drift matters

A scheduled job can change behavior after package upgrades.

A diagnostic wrapper can record:

```bash
/usr/bin/python3 --version
/usr/bin/curl --version | head -n 1
/usr/bin/rsync --version | head -n 1
```

For long-term reproducibility, application deployment metadata may include:

```text
git commit
package version
container image digest
build identifier
```

Example:

```bash
logger -t report \
    "event=start app_version=$(cat /srv/report/VERSION)"
```

When a cron job suddenly fails after months of stability, version information can quickly connect the failure to a deployment or system upgrade.

## Cron jobs can inherit failure from unavailable services

Suppose:

```cron
5 0 * * * /opt/jobs/report
```

starts immediately after midnight.

The report depends on PostgreSQL.

If PostgreSQL is restarting due to nightly maintenance, the job fails.

This is not necessarily a cron problem.

Add bounded retries when transient failure is expected.

Example:

```bash
#!/bin/sh
set -eu

attempt=1
max=5

while [ "$attempt" -le "$max" ]; do
    if /usr/bin/pg_isready -q; then
        exec /opt/jobs/report-real
    fi

    echo "database unavailable attempt=$attempt" >&2
    sleep 30
    attempt=$((attempt + 1))
done

echo "database unavailable after $max attempts" >&2
exit 50
```

Do not implement infinite retries inside cron.

Bound retries so failure remains visible.

For dependency-aware scheduling, systemd timers and services may provide stronger semantics.

## Avoid hiding errors behind `|| true`

This pattern is dangerous:

```bash
/opt/jobs/sync || true
```

It deliberately turns failure into success.

There are legitimate cases:

```bash
rm -f /tmp/nonexistent || true
```

but overuse makes monitoring meaningless.

If failure is expected and non-fatal, handle it explicitly:

```bash
if ! /opt/jobs/cleanup-old-cache; then
    echo "cache cleanup failed but report will continue" >&2
fi

/opt/jobs/build-report
```

Now the script communicates which failure is tolerated and which one determines the final status.

Error suppression should be narrow and documented.

## Beware of commands where non-zero does not mean "error"

Some Unix utilities use non-zero statuses for normal boolean results.

`grep` commonly returns:

```text
0 = match found
1 = no match
2 = error
```

This script:

```bash
set -e
grep -q pattern file
echo continue
```

exits if the pattern is absent, even though "no match" may be expected.

Handle semantics:

```bash
if grep -q pattern file; then
    echo "found"
else
    rc=$?

    if [ "$rc" -eq 1 ]; then
        echo "not found"
    else
        echo "grep failed rc=$rc" >&2
        exit "$rc"
    fi
fi
```

Similarly:

```text
diff
test
cmp
```

may use non-zero statuses as meaningful comparison outcomes.

A cron wrapper should understand the commands it uses rather than treating every non-zero code identically.

## Record host identity in multi-server environments

If logs from many servers enter the same platform, record:

```text
hostname

```

Example:

```bash

    "host=$HOST event=start"
```

Without host context, this message:

```text

```

is almost useless in a fleet.

With:

```text
host=db-03 env=prod job=backup rc=28
```

the incident becomes actionable.

## Clock accuracy matters when correlating logs

Cron schedules and log timestamps depend on system time.

Check:

```bash
timedatectl
```

and:

```bash
timedatectl timesync-status
```

where available.

If one server is several minutes out of sync, correlated logs may appear to show events in the wrong order.

This matters in distributed failures:

```text
cron launch on app server
API request on gateway
database transaction
object storage upload
```

Reliable NTP/time synchronization is part of observability infrastructure.

## A cron job can run twice because of duplicate definitions

Suppose logs show:

```text
02:00 started
02:00 started
```

Do not immediately assume cron duplicated the same entry.

Search all possible sources:

```bash
crontab -l
sudo crontab -l
sudo grep -R -n "backup.sh" /etc/cron* 2>/dev/null
systemctl list-timers --all | grep -i backup
```

Possible duplication:

```text
user crontab
root crontab
/etc/crontab
/etc/cron.d/
cron.daily
systemd timer
application scheduler
container scheduler
cloud scheduler
```

A deployment migration can leave both old and new scheduling mechanisms active.

Logging unique run IDs and process identity makes duplicate execution easier to prove.

## Log the parent process during difficult investigations

Inside a script:

```bash
echo "pid=$$ ppid=$PPID"
```

For deeper inspection:

```bash
ps -o pid,ppid,user,cmd -p "$$" -p "$PPID"
```

A typical process tree might show:

```text
cron
  \_ /bin/sh -c /opt/jobs/task.sh
      \_ /bin/bash /opt/jobs/task.sh

```

Inspect:

```bash
pstree -aps $$
```

This helps distinguish:

```text
cron-launched execution
manual test
systemd service
container entrypoint
```

when the same script can be started from multiple paths.

## Detect overlap through process inspection

Suppose a job runs every minute:

```cron
* * * * * /opt/jobs/sync
```

but sometimes takes four minutes.

Check:

```bash
pgrep -af '/opt/jobs/sync'
```

If several copies appear, you have an overlap problem.

Count them:

```bash
pgrep -fc '/opt/jobs/sync'
```

Be careful with process matching because pattern-based searches can match wrapper shells or unrelated commands.

A lock is more reliable than process-name detection.

The dedicated concurrency chapter will cover this deeply, but from a diagnostic perspective:

```text
repeated start logs without finish logs
multiple PIDs
growing load
duplicate application effects
```

are classic indicators of overlapping cron executions.

## Check load and I/O pressure

A cron job can appear slow because the server is under resource pressure.

CPU/load:

```bash
uptime
```

Processes:

```bash
top
```

or:

```bash
ps -eo pid,user,pcpu,pmem,stat,etime,cmd \
    --sort=-pcpu \
    | head
```

Memory:

```bash
free -h
```

Disk:

```bash
iostat -xz 1
```

if `sysstat` is installed.

I/O per process:

```bash
iotop
```

with appropriate privileges.

A nightly backup competing with:

```text
database vacuum
log compression
filesystem scrub
snapshot creation
another backup
```

can become dramatically slower without any code regression.

Scheduling is also resource orchestration.

## Check system logs around the failure window

Instead of only reading cron logs:

```bash
journalctl \
    --since "2026-09-13 01:50:00" \
    --until "2026-09-13 02:20:00"
```

Look for:

```text
disk errors
OOM events
network changes
mount failures
service restarts
kernel warnings
authentication failures
SELinux/AppArmor denials
```

A broad time-window view often reveals the external event that caused the scheduled task to fail.

Then narrow with:

```bash
journalctl -p warning \
    --since "2026-09-13 01:50:00" \
    --until "2026-09-13 02:20:00"
```

Time correlation is one of the strongest incident-debugging techniques.

## Preserve enough logs for intermittent failures

A job that fails once every two weeks is difficult to debug if logs rotate after one day.

Retention should match failure frequency and business importance.

For example:

```text
hourly health check -> maybe 7-14 days of detailed logs
daily backup -> maybe 30-90 days of metadata
monthly financial export -> possibly much longer audit retention
```

Do not keep sensitive full logs forever without reason.

Retention should balance:

```text
diagnostic value
storage cost
privacy
security
compliance
```

Operational logging is a lifecycle, not just a file destination.

## Avoid logging secrets

A debugging line like:

```bash
env
```

can expose:

```text
database passwords
API tokens
cloud credentials
private endpoints
session keys
```

This is particularly dangerous if output is redirected to:

```text
/tmp/debug.log
```

with weak permissions.

Instead, log selected safe variables:

```bash
printf 'PATH=%s\n' "$PATH"
printf 'HOME=%s\n' "$HOME"
printf 'APP_ENV=%s\n' "${APP_ENV:-unset}"
```

Do not print:

```text
AWS_SECRET_ACCESS_KEY
DATABASE_URL with password
Authorization headers
private keys
tokens
```

Likewise, avoid:

```bash
set -x
```

around secret-bearing commands.

Observability must not become a credential leak.

## File permissions for cron logs matter

Create a sensitive log safely:

```bash
sudo install \
    -o root \
    -g adm \
    -m 0640 \
    /dev/null \
    /var/log/company-backup.log
```

Now only root and members of the chosen administrative group can read it.

A log containing:

```text
customer identifiers
internal hostnames
database errors
file paths
request details
```

can reveal useful information to an attacker even without explicit passwords.

Logs are security-sensitive data.

Use:

```bash
stat /var/log/company-backup.log
```

and audit logrotate's `create` mode so rotation does not accidentally recreate the file as world-readable.

## A diagnostic wrapper for arbitrary cron commands

A general-purpose wrapper can help while debugging.

Example:

```bash
#!/usr/bin/env bash
set -u

LOG=/var/log/cron-debug.log
START=$(date +%s)

{
    echo "===== START $(date -Is) ====="
    echo "pid=$$"
    echo "ppid=$PPID"
    echo "uid=$(id -u)"
    echo "user=$(id -un)"
    echo "groups=$(id -Gn)"
    echo "pwd=$PWD"
    echo "shell=$SHELL"
    echo "path=$PATH"
    echo "umask=$(umask)"
    echo
} >> "$LOG"

"$@" >> "$LOG" 2>&1
rc=$?

END=$(date +%s)

{
    echo
    echo "rc=$rc"
    echo "duration_seconds=$((END-START))"
    echo "===== END $(date -Is) ====="
    echo
} >> "$LOG"

exit "$rc"
```

Install:

```bash
sudo install -o root -g root -m 0755 \
    cron-debug-wrapper \
    /usr/local/sbin/cron-debug-wrapper
```

Use temporarily:

```cron
* * * * * /usr/local/sbin/cron-debug-wrapper /opt/jobs/task
```

Do not leave broad diagnostic logging enabled indefinitely, especially if command output contains sensitive data.

## A debugging workflow for "works manually, fails in cron"

Start by proving the schedule:

```bash
journalctl -u cron --since "30 minutes ago"
```

Confirm:

```text
CMD (...)
```

appears.

Then capture output:

```cron
* * * * * /opt/jobs/task >> /tmp/task-debug.log 2>&1
```

Test as the user:

```bash
sudo -u USER /opt/jobs/task
```

Test minimal environment:

```bash
sudo -u USER env -i \
    HOME=/home/USER \
    USER=USER \
    LOGNAME=USER \
    PATH=/usr/bin:/bin \
    SHELL=/bin/sh \
    /opt/jobs/task
```

Inspect:

```bash
head -n 1 /opt/jobs/task
namei -l /opt/jobs/task
file /opt/jobs/task
```

Check application dependencies:

```bash
command -v required-tool
```

as the actual user and environment.

Check system-level events:

```bash
journalctl \
    --since "30 minutes ago" \
    -p warning
```

Only after gathering evidence should you modify the job.

This sequence avoids changing several variables at once and destroying the original failure condition.

## Prefer explicit health checks over absence-of-error assumptions

Bad monitoring:

```text
No cron email arrived, therefore the backup succeeded.
```

Better monitoring:

```text
A backup artifact newer than 26 hours exists.
Archive integrity check passes.
Artifact size is within expected range.
Remote copy exists.
Last run recorded rc=0.
Restore test succeeded recently.
```

The absence of an error signal is weak evidence.

Positive verification is stronger.

For a simple file freshness check:

```bash
find /var/backups/app \
    -type f \
    -name 'app-*.tar.gz' \
    -mmin -1560 \
    -print \
    -quit
```

If no path is returned, alert.

This separates:

```text
scheduler monitoring
outcome monitoring
```

Both are valuable.

## Use sentinel files carefully

Some systems create:

```text
/var/lib/job/last-success
```

on successful completion:

```bash
touch /var/lib/job/last-success
```

Monitoring checks its timestamp:

```bash
stat /var/lib/job/last-success
```

This is simple and effective for some jobs.

But update it only after all required work is complete.

Bad:

```bash
touch /var/lib/job/last-success
perform_backup
upload_backup
```

Good:

```bash
perform_backup
upload_backup
verify_backup
touch /var/lib/job/last-success
```

The sentinel represents successful completion, so its update belongs at the end of the success path.

## Separate `last-start`, `last-success`, and `last-failure`

For more visibility:

```text
/var/lib/job/last-start
/var/lib/job/last-success
/var/lib/job/last-failure
```

A wrapper:

```bash
#!/bin/sh

STATE=/var/lib/report-job
mkdir -p "$STATE"

date -Is > "$STATE/last-start"

/opt/jobs/report
rc=$?

if [ "$rc" -eq 0 ]; then
    date -Is > "$STATE/last-success"
else
    {
        echo "date=$(date -Is)"
        echo "rc=$rc"
    } > "$STATE/last-failure"
fi

exit "$rc"
```

Monitoring can detect:

```text
started recently but no success
last success too old
recent failure
```

For large-scale systems, metrics are better, but state files are a useful lightweight technique.

## Atomic state updates prevent partial metadata

Instead of:

```bash
echo "$data" > /var/lib/job/state
```

use:

```bash
tmp=$(mktemp /var/lib/job/.state.XXXXXX)
printf '%s\n' "$data" > "$tmp"
mv "$tmp" /var/lib/job/state
```

This prevents readers from observing a partially written state file.

The rename is atomic when source and destination are on the same filesystem.

Cron jobs often run concurrently with monitoring agents, so atomic updates matter.

## Monitor skipped runs too

A job protected by a lock may exit because another instance is already running.

That is not necessarily an error.

But repeated skips can indicate that runtime exceeds the schedule interval.

Example log:

```text
event=skip reason=lock_held
```

Monitor how often this happens.

A daily job skipped once because an administrator manually triggered it may be fine.

A five-minute job skipped for six consecutive hours indicates a serious operational issue.

Observability should distinguish:

```text
success
failure
skipped
timed out
cancelled
```

rather than compressing every outcome into success/failure.

## Monitoring cron with a heartbeat endpoint

Some teams use a monitoring service where the job sends a signal on completion.

Conceptually:

```bash
run_job
rc=$?

if [ "$rc" -eq 0 ]; then
    curl --fail --silent \
        https://monitor.example/success/JOB_ID
else
    curl --fail --silent \
        https://monitor.example/fail/JOB_ID
fi

exit "$rc"
```

This can detect a more important failure class:

```text
the job did not run at all
```

because the monitoring service expects a heartbeat within a time window.

Be careful not to let failure of the monitoring HTTP request replace the real application's exit status unintentionally.

For example:

```bash
run_job
rc=$?

send_monitoring_event "$rc" || true

exit "$rc"
```

may be appropriate if monitoring transport failure should not change job outcome.

But that monitoring failure should be logged elsewhere.

## Metrics provide stronger long-term observability

For important scheduled workloads, expose metrics such as:

```text
cron_job_last_start_timestamp
cron_job_last_success_timestamp
cron_job_last_failure_timestamp
cron_job_duration_seconds
cron_job_exit_code
cron_job_runs_total
cron_job_failures_total
cron_job_processed_items
```

A monitoring system can alert:

```text
last_success > expected interval
failure counter increased
duration exceeds threshold
processed items unexpectedly zero
```

This is much stronger than grepping text logs manually.

Cron can remain the scheduler while modern monitoring handles execution history.

## A minimal job can still be well observed

Not every script needs a large framework.

Example:

```bash
#!/bin/sh
set -eu

JOB=cache-clean

/usr/bin/logger -t "$JOB" "start"

/usr/bin/find /var/cache/app \
    -type f \

```

Cron:

```cron

```

For a simple deterministic maintenance command, that may be sufficient.

Engineering effort should match risk.

A root filesystem cleanup job deserves more care than a harmless personal reminder.

Create:

```bash
mkdir -p /tmp/cron-failure-lab
```

Script:

```bash
cat > /tmp/cron-failure-lab/job.sh <<'EOF'
#!/bin/sh
```

```bash

```


must be designed together.

## A compact production logging pattern

For many scheduled shell jobs, a strong baseline is:

```bash
#!/usr/bin/env bash
set -Eeuo pipefail

JOB=example-job
START=$(date +%s)
RUN_ID="$(date -u +%Y%m%dT%H%M%SZ)-$$"

finish() {
    rc=$?
    end=$(date +%s)

    if (( rc == 0 )); then
        priority=user.info
        event=finish
    else
        priority=user.err
        event=fail
    fi

    logger -p "$priority" -t "$JOB" \
        "run_id=$RUN_ID event=$event rc=$rc duration_seconds=$((end-START))"

    exit "$rc"
}

trap finish EXIT

logger -t "$JOB" \
    "run_id=$RUN_ID event=start"

do_work
```

This is not mandatory boilerplate for every cron script, but it demonstrates useful principles:

```text
start event
finish/failure event
unique run ID
exit code
duration
system logging
exit-status preservation
```

Adapt it to the complexity and sensitivity of the job.

## A practical incident example

Imagine a production database backup normally runs at 01:30.

At 08:00 monitoring reports no fresh backup.

The cron entry is:

```cron
30 1 * * * postgres /usr/local/libexec/db-backup
```

A disciplined investigation might look like this.

Check scheduler:

```bash
systemctl status cron
```

Active.

Check scheduler log:

```bash
journalctl -u cron \
    --since "01:20" \
    --until "01:45"
```

You see:

```text
(postgres) CMD (/usr/local/libexec/db-backup)
```

Therefore cron launched the job.

Check application tag:

```bash
journalctl -t db-backup \
    --since "01:20" \
    --until "02:30"
```

Output:

```text
event=start run_id=...
```

but no finish event.

Find historical kernel events:

```bash
journalctl -k \
    --since "01:20" \
    --until "02:30" \
    | grep -i -E 'oom|killed process'
```

You discover:

```text
Out of memory: Killed process ... pg_dump
```

The incident is not:

```text
cron failed
```

It is:

```text
cron successfully started a backup
the backup process was killed by the kernel because of memory pressure
```

Those are completely different remediation paths.

One may lead to:

```text
memory tuning
backup strategy change
job scheduling separation
resource limits
server capacity
```

instead of changing crontab syntax.

Good logs prevent category errors.

## Another incident example: backup "succeeds" to the wrong filesystem

Cron:

```cron
0 2 * * * root /usr/local/sbin/archive
```

Log:

```text
archive finished rc=0
```

But off-host backup storage shows nothing.

Inspect script:

```bash
rsync -a /srv/data/ /mnt/backup/data/
```

Check:

```bash
mountpoint /mnt/backup
```

Output indicates it is not a mountpoint.

The remote disk failed to mount during boot, but the directory:

```text
/mnt/backup
```

still existed locally.

`rsync` copied data successfully onto the root filesystem.

Therefore:

```text
process success = yes
business success = no
```

The corrected script checks:

```bash
mountpoint -q /mnt/backup || exit 1
```

before copying.

This is a perfect example of why logs need domain validation, not only exit codes.

## Another incident example: silent HTTP authentication failure

Cron:

```cron
*/15 * * * * /opt/jobs/pull-inventory
```

The script:

```bash
curl -s https://inventory.example/api/items \
    > /var/lib/app/items.json
```

Monitoring sees the file updated every fifteen minutes.

Everything appears healthy.

A later inspection shows:

```json
{"message":"token expired"}
```

The file is fresh, but the data is invalid.

Fix:

```bash
curl \
    --fail \
    --show-error \
    --silent \
    -H "Authorization: Bearer $TOKEN" \
    https://inventory.example/api/items \
    > "$tmp"
```

Then parse/validate expected schema before replacing the production file.

Fresh timestamps alone are not sufficient validation.

## Troubleshooting should preserve the failure

When investigating a failing cron job, avoid immediately changing:

```text
user
PATH
shell
working directory
permissions
schedule
script
logging
```

all at once.

If five things change and the job starts working, you do not know what the root cause was.

A better sequence:

```text
capture current evidence
reproduce under same user
reproduce under minimal environment
change one variable
repeat
```

This is basic experimental discipline.

Cron troubleshooting is much faster when treated like a controlled systems experiment.

---

## Avoid one-minute production test jobs that you forget to remove

During debugging:

```cron
* * * * * /opt/jobs/backup
```

is convenient.

If the original schedule was:

```cron
0 2 * * * /opt/jobs/backup
```

forgetting the temporary minute schedule can create catastrophic load.

Prefer a harmless probe:

```cron
* * * * * /usr/bin/logger -t cron-test "probe"
```

or manually run the real job under the correct environment.

If you must temporarily increase frequency, document it and remove it immediately after the test.

Search afterwards:

```bash
crontab -l
sudo grep -R -n '/opt/jobs/backup' /etc/cron* 2>/dev/null
```

Production debugging should not create a second incident.

## A practical observability checklist

For an important cron job, you should be able to answer:

```text
Where is the schedule defined?
Which user runs it?
How do I prove cron attempted to start it?
Where does stdout go?
Where does stderr go?
How is log retention handled?
Where is the application's own log?
What exit codes can the application return?
Is the exit status preserved by wrappers and pipelines?
How do I identify one specific run?
Is duration recorded?
How do I detect a missing run?
How do I detect a false-success run?
How do I detect overlapping runs?
What artifact proves success?
How is that artifact validated?
Are credentials excluded from logs?
Can I reproduce the exact execution environment manually?
```

If most answers are unknown, the job may work today but will be expensive to debug later.

## Final perspective

Cron failures are often described too vaguely.

People say:

```text
cron didn't run
```

when the actual event was:

```text
cron ran the command
the shell started
the program connected to a database
the database query succeeded
the upload process hung
the timeout killed it
stderr was discarded
no monitoring checked the result
```

Those details matter.

A scientific troubleshooting approach follows observable state through the entire execution chain:

```text
schedule
process creation
identity
environment
program execution
dependencies
output
exit status
artifact
monitoring
```

Logging should answer what happened.

Exit status should tell machines whether the process succeeded.

Application validation should tell operators whether the intended work succeeded.

Retention should preserve enough history to investigate intermittent faults.

Monitoring should detect both explicit failures and missing executions.

And diagnostics should preserve evidence without exposing secrets.

When those properties are designed into a scheduled task, cron becomes easy to operate because failure is visible, classifiable, and reproducible.

The hardest cron incidents are rarely caused by the five scheduling fields.

They are caused by invisible execution failures.

Good observability makes them visible.
