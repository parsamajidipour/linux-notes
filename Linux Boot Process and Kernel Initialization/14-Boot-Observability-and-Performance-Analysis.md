# Boot Observability and Performance Analysis

Boot is difficult to observe because the tools used for observation are created during the event being observed.

Firmware may have only a debug port. A loader has its own console. Early kernel code may have no normal driver. printk records appear before persistent storage. Initramfs has a temporary root and logging stack. PID 1 later merges, forwards, or persists messages. Timing sources also change.

Good boot analysis therefore uses several evidence channels and names their clocks and boundaries. This chapter develops a reproducible method for correctness and performance work without confusing a quiet console with an idle machine or a long service with a critical delay.

---

## 1. Build an observability ladder

Use the earliest channel available for the suspected stage:

1. board POST codes, BMC logs, or firmware debug serial;
2. UEFI console and firmware boot-manager status;
3. loader console and debug messages;
4. architecture early console;
5. kernel printk consoles;
6. pstore or crash capture;
7. initramfs logs and emergency shell;
8. journald kernel and userspace records;
9. systemd-analyze and unit timing;
10. tracing and profiling.

A later channel cannot recover data never stored. If the CPU resets during decompression, journalctl has no previous-boot record to read. If PID 1 starts, later tools can expose buffered kernel messages that were not visible on screen.

Select evidence based on the last boundary, not familiarity.

---

## 2. printk records and console output

printk creates log records with priority, facility, text, and timing metadata. Consoles consume eligible records according to log level. The ring buffer and visible console are separate.

quiet reduces console chatter. loglevel=N controls which severities print. ignore_loglevel asks consoles to print broadly for debugging. none necessarily causes more messages to be generated by every subsystem.

After boot:

~~~sh
dmesg --level=emerg,alert,crit,err,warn
journalctl -b -k
cat /proc/sys/kernel/printk
~~~

dmesg access can be restricted. journald may contain kernel records with structured metadata and boot ID.

Printing is not free. A slow serial console can dramatically extend boot when verbose logging is enabled. Compare performance with equivalent logging policy.

---

## 3. Boot consoles and real consoles

An early console or boot console uses minimal polling code before normal drivers register. Later, a real console driver takes ownership. The kernel can replay buffered records to the new console.

If output stops exactly at handoff, possibilities include:

- normal console parameter points elsewhere;
- real driver failed probe;
- baud or mode mismatch;
- graphical console replaced text;
- output continues only in buffer;
- machine actually hung at a nearby point.

Use multiple channels. A serial console plus virtual VGA in a VM can distinguish console loss from execution loss.

console= may be specified multiple times for output. The last eligible console of a type often becomes preferred for /dev/console input semantics, with nuances documented in serial-console guidance.

## 4. earlycon

earlycon initializes a supported early console using firmware description or explicit parameters. It works before the full tty and driver stack.

Examples are platform-specific:

~~~text
earlycon
earlycon=uart8250,io,0x3f8,115200
console=ttyS0,115200n8
~~~

The second suits a conventional emulated PC UART, not arbitrary hardware. Device Tree stdout-path and ACPI SPCR can provide data on supported systems.

An invalid MMIO address can fault or hang, so do not guess. Use platform documentation and a disposable test.

Keep earlycon only as long as needed; polling can affect timing and expose sensitive addresses or messages.

---

## 5. initcall_debug

The initcall_debug parameter logs initcall entry, return, duration, and process context. It identifies a built-in function that blocks or fails.

~~~text
initcall_debug ignore_loglevel
~~~

Interpret carefully:

- duration can include intentional hardware waits;
- asynchronous work launched by an initcall may finish later;
- console overhead inflates measurements;
- one slow call may run in parallel with a longer critical dependency elsewhere;
- function names need matching source and configuration.

Use it to locate, then use subsystem tracing or driver debug for causality.

---

## 6. Dynamic debug

Kernel dynamic debug enables selected pr_debug and dev_dbg call sites at runtime or through boot parameters.

The control file under debugfs can select by module, file, function, or format. A boot-time dyndbg parameter enables messages early enough for built-in drivers.

Target narrowly. Enabling every call site produces enormous logs, changes timing, and can hide the event in noise.

Conceptual boot parameter:

~~~text
dyndbg="file drivers/nvme/host/* +p"
~~~

Quoting must survive the loader parser. Confirm syntax against current dynamic-debug documentation.

---

## 7. ftrace boot tracing

ftrace can record function execution, events, and latency inside the kernel. Boot-time tracing configures it before userspace is available through command-line parameters or bootconfig.

Useful tracers and events include:

- function graph for selected functions;
- initcall events;
- scheduler wakeups and switches;
- IRQ and softirq events;
- workqueue events;
- block I/O;
- power and CPU frequency;
- device power-management callbacks.

Tracing every function from boot can overflow buffers and distort timing. Filter by subsystem and choose a buffer size that fits memory.

After boot, tracefs normally exposes captured data under /sys/kernel/tracing. Preserve it before starting unrelated workload.

---

## 8. Bootconfig

Bootconfig appends structured key-value configuration to the initrd or supplies it through supported mechanisms, allowing readable hierarchical tracing configuration beyond a long flat command line.

It is particularly useful for ftrace boot setup: select events, filters, actions, buffer sizes, and start/stop conditions.

The kernel must be built with bootconfig support, and the loader/image build must attach the data correctly. xbc-related tools validate syntax.

Bootconfig is still boot input. If security depends on tracing or policy keys, authenticate the configuration with the boot artifact.

---

## 9. pstore

pstore preserves crash or firmware records across reboot using persistent RAM, EFI variables, or platform backends. ramoops reserves a RAM region for console, panic, and ftrace data.

After reboot, records may appear under /sys/fs/pstore and be collected by system services.

~~~sh
find /sys/fs/pstore -maxdepth 1 -type f -ls 2>/dev/null
~~~

Capacity is small. Use concise panic and console capture. Correct reserved-memory configuration is essential; ordinary allocation must not overwrite the area.

pstore is valuable when the system resets before disk logging. It does not replace crash dumps for full memory analysis.

---

## 10. kdump

kdump reserves memory for a crash kernel. When the production kernel panics, kexec transfers to the preloaded crash kernel, which writes a vmcore without trusting the failed kernel's drivers and state.

Requirements include:

- crashkernel memory reservation at boot;
- a crash kernel and initramfs capable of writing the dump target;
- kexec and signature/lockdown policy compatibility;
- storage or network path independent enough to work after failure;
- tested trigger and collection.

The crash kernel is a different kernel boot path that bypasses normal firmware. Its device state can be unusual. Test rather than assuming configuration files imply success.

vmcore plus matching vmlinux and debug symbols supports crash utility or GDB analysis.

---

## 11. Journald boot identities

systemd-journald attaches a boot ID to records. Persistent storage lets journalctl inspect previous boots:

~~~sh
journalctl --list-boots
journalctl -b -1 -k
journalctl -b 0 -o short-monotonic
~~~

If /var/log/journal is unavailable early, records begin in volatile storage and may later flush to disk. A crash before flush can lose them.

The kernel ring buffer, journal, and traditional text logs may contain overlapping but not identical data. Use the journal boot ID to avoid mixing restarts.

---

## 12. Clock domains

Firmware, loader, kernel, and userspace may report different clocks.

- firmware time often measures from platform-specific reset or phase boundaries;
- loader time uses firmware timers or its own base;
- kernel printk commonly shows monotonic time since a kernel reference point;
- boottime includes suspend where monotonic may exclude it in API terms;
- realtime is wall clock and can jump after RTC/NTP correction;
- systemd correlates firmware, loader, kernel, initrd, and userspace when metadata is available.

Never subtract timestamps across domains without a documented correlation. A log line at kernel 1.2 seconds and a firmware report of 8 seconds do not imply total 9.2 unless their definitions align.

Use monotonic format for ordering:

~~~sh
journalctl -b -o short-monotonic
dmesg --time-format=delta
~~~

---

## 13. systemd-analyze time

systemd-analyze time reports intervals such as firmware, loader, kernel, initrd, and userspace when available.

~~~sh
systemd-analyze time
~~~

The userspace endpoint is generally when the default target's queued work completes, not when every background service is idle or an application health check passes.

Firmware and loader measurements depend on EFI variables and loader support. Missing values mean unavailable data, not zero time.

Compare same machine, firmware settings, boot mode, and endpoint. Cold and warm boots differ.

---

## 14. blame and critical-chain

~~~sh
systemd-analyze blame
systemd-analyze critical-chain
~~~

blame sorts unit activation duration. It can unfairly blame a unit waiting for an event and omits time not attributed to a unit.

critical-chain follows ordering dependencies constraining a target. A 20-second service running in parallel may not delay the target; a 2-second unit on the serial chain may.

Socket activation can mark a unit active before its service completes work. Type=simple considers startup differently from Type=notify. Understand service readiness semantics before optimizing numbers.

The systemd section of this repository explains the transaction graph in depth.

## 15. Plotting the userspace path

systemd-analyze plot produces SVG showing unit timing and dependency relationships:

~~~sh
systemd-analyze plot > boot.svg
~~~

Generating a report file is safe; opening and interpreting it is the work. Look for serialization, long device waits, repeated timeouts, and services starting earlier than necessary.

The plot begins after systemd has data. It does not explain firmware, decompression, or most initramfs unless integrated timing is present.

Security-sensitive unit names and timing can reveal system roles; sanitize before sharing.

## 16. Device and block timing

Storage delays can originate in controller probe, link reset, partition reading, udev, encryption, filesystem recovery, or I/O congestion.

Evidence sources:

- kernel timestamps around controller and block registration;
- udev monitor timing;
- initramfs debug logs;
- block tracepoints;
- filesystem mount/recovery messages;
- device-unit activation timing.

Do not infer "slow disk" from a late mount alone. The disk may be idle while early userspace waits for a passphrase or missing UUID.

Trace only the relevant device in a lab. Full block tracing during boot can generate large data.

---

## 17. Firmware and loader timing

UEFI can publish timestamps consumed by supporting loaders and systemd. Firmware setup may also show last boot duration. These values can include memory training, device enumeration, network attempts, and vendor delays.

To isolate:

1. measure power to loader menu with an external camera or serial timestamps;
2. disable one unused firmware boot option at a time;
3. compare cold boot and warm reboot;
4. record firmware version and settings;
5. keep OS artifacts constant.

Fast Boot options may skip initialization needed by other operating systems or removable devices. A lower number is not automatically a better or safer configuration.

---

## 18. Reproducible performance method

Define the question: "reduce cold power-on to SSH-ready p95 from 42 to 30 seconds" is measurable; "make boot faster" is not.

Then:

1. choose cold or warm start;
2. define start and end events;
3. perform multiple runs;
4. record median, spread, and outliers;
5. retain firmware, loader, kernel, initramfs, and unit versions;
6. change one variable;
7. measure again;
8. check correctness and security regressions.

Caches, entropy, DHCP, storage recovery, network availability, and update jobs introduce variance. One fast run is not a result.

Prefer removing unnecessary serialized dependencies over disabling safety checks. A skipped filesystem or integrity check can buy time by accepting risk.

## 19. Worked example: ninety-second boot delay

systemd reports a device unit timing out near ninety seconds. The root is already mounted; a data disk listed in fstab is absent.

Boundary evidence:

- firmware, loader, kernel, initramfs, and PID 1 succeeded;
- the wait is a generated mount dependency;
- the timeout dominates the critical chain to the target.

Repair options depend on policy: correct the UUID, reconnect the disk, mark it nofail when boot need not depend on it, shorten a justified timeout, or use automount. Disabling unrelated services does not address the serialized missing device.

After change, verify application behavior. A database may require the mount even if the boot target no longer waits.

---

## 20. Worked example: kernel gap during storage probe

Kernel timestamps show ten seconds between controller reset and device registration. initcall_debug names the driver initcall, and dynamic debug shows repeated reset polling.

Possible causes include controller firmware, link negotiation, error recovery, missing device, or driver regression. Compare previous kernel and firmware, cold versus warm boot, and hardware health.

Do not optimize by reducing timeout until you know why the controller needs it. A shorter timeout can make marginal hardware disappear instead of boot faster.

---

## 21. Failure evidence preservation

Before rebooting a partially working system:

~~~sh
dmesg > /run/dmesg-current.txt
journalctl -b > /run/journal-current.txt
cat /proc/cmdline > /run/cmdline-current.txt
systemd-analyze dump > /run/systemd-dump.txt 2>/dev/null
~~~

Copy files to safe storage if /run is volatile. Avoid shell redirection to a failing or read-only filesystem.

Photograph exact panic text when no capture exists. Include the first error, not only the final panic. Later errors are often consequences.

After reboot, check pstore and the previous journal before another boot rotates evidence.

---

## 22. Common measurement mistakes

- Comparing a cold boot with a warm reboot.
- Enabling verbose serial logging in only one run.
- Treating systemd-analyze blame as a dependency proof.
- Adding firmware, kernel, and wall-clock values from unrelated bases.
- Measuring until a desktop appears visually instead of a defined event.
- Optimizing averages while ignoring intermittent timeout outliers.
- Disabling verification, recovery, or watchdogs for a cosmetic number.
- Profiling a debug kernel and applying absolute timings to production.
- Forgetting that tracing buffer overflow drops early events.

Write methodology beside results.

---

## 23. Mechanism summary

Boot observability is staged. Firmware, loader, early console, printk, pstore, initramfs logs, journal, and tracing each cover different intervals. The kernel log buffer is distinct from console output. Clocks have different origins. systemd timing explains a userspace dependency graph, not the whole power-on path.

A scientific analysis defines boundaries, preserves raw evidence, repeats equivalent starts, changes one variable, and checks correctness after optimization. The next chapter applies that method to a catalog of failures and a conservative recovery workflow.

## Primary references

## 24. Designing a boot trace

Begin with a hypothesis, not every event. Suppose root appears five seconds after the NVMe controller logs successful probe. The gap may be partition scanning, udev, cryptsetup, LVM, or filesystem work.

Choose tracepoints around those boundaries: block device add, uevents, workqueue execution, device-mapper operations, and scheduler wakeups for the relevant processes. Filter by device or process where possible. Allocate a buffer large enough and use a stop trigger after the root mount event so later services do not overwrite evidence.

Record trace clock selection. A local per-CPU clock may need synchronization for cross-CPU ordering; a global clock can cost more. Save kernel build, trace configuration, command line, and dropped-event statistics.

After capture, build a causal timeline:

~~~text
controller probe complete
namespace registered
partition uevent emitted
udev rule begins
cryptsetup process wakes
dm-crypt mapping appears
LVM scan begins
root LV activated
mount syscall begins/ends
~~~

The first large interval identifies the layer. Trace data is evidence of execution, not automatically explanation: a sleeping process might wait for user input, I/O, a mutex, or timer. Inspect wakeup source and stack where available.

## 25. External measurement

Internal clocks miss power-on time and can be biased by the system under test. External measurement provides an independent endpoint.

Options include a camera recording power LED and console, a serial capture host with its own monotonic timestamps, a network probe from another machine, a smart power controller, or a hardware logic signal in embedded systems.

For service readiness, probe an actual application transaction rather than only TCP port open. Socket activation can accept connections before the service finishes initialization. Define success as a correct response and record failures during the interval.

Correlate external and internal timelines with a visible marker, such as a loader serial line and a userspace message sent to the same capture host. Do not force wall clocks to synchronize during the measured interval and then mistake the correction for performance.

## 26. Statistical treatment

Boot times are distributions. Report at least sample count, median, percentile or range, and start condition. A single ninety-second timeout among twenty five-second boots matters operationally even if the mean seems acceptable.

Separate cold boots, warm reboots, and hibernation. Randomize A/B test order so temperature, caches, and network state do not systematically favor one version. Avoid running benchmarks immediately after updates only on one branch.

Use confidence intervals or nonparametric comparison when variance is high. More importantly, inspect modes: bimodal timing often reveals a timeout path or race. Performance engineering should explain the distribution shape, not only lower an average.

## 27. Performance changes and correctness

For every proposed optimization, write the removed guarantee:

- disabling fsck removes pre-mount consistency validation;
- reducing device timeout abandons slower-but-valid hardware sooner;
- removing initramfs modules reduces migration/recovery compatibility;
- disabling Secure Boot removes first-stage authentication;
- skipping network-online changes service readiness ordering;
- parallelizing units can expose an undeclared dependency;
- disabling a watchdog removes automatic recovery from hangs.

Sometimes the trade is acceptable. The requirement is explicit ownership and fallback. A laptop can defer an optional network mount; a database server may not.

After a timing improvement, run failure tests. Disconnect the optional disk, make DHCP unavailable, boot the fallback kernel, and interrupt an update. A faster normal path that destroys recovery is a regression.

## 29. Privacy and security of traces

Boot logs can contain serial numbers, filesystem UUIDs, network addresses, command lines, crash addresses, usernames, device topology, and sometimes secrets supplied incorrectly as parameters. Traces can contain filenames and process activity. Firmware variables can expose certificates and asset details.

Store raw artifacts with incident-data controls. Redact copies, not originals. Preserve stable pseudonyms so relationships remain analyzable. Do not paste full dmesg or efibootmgr output publicly without review.

Reducing kptr_restrict or lockdown for profiling changes security posture. Perform it on isolated labs and restore policy. Observability is part of the attack surface; the best tool is the narrowest one that answers the question.

## 24. Designing a focused trace

Start with a hypothesis. If root appears five seconds after NVMe probe, trace block registration, uevents, workqueues, device mapper, and scheduler wakeups for relevant processes. Filter by device or PID where possible and stop capture after root mount so later services do not overwrite evidence.

Record trace clock, buffer size, filters, dropped events, kernel build, and command line. Build a causal timeline from controller probe through namespace, partition, udev, cryptsetup, LVM, and mount.

A sleeping process can wait for I/O, input, mutex, or timer. Trace execution shows where time passed; wakeup source and stack explain why.

## 25. External measurement

Internal clocks omit early power-on and can be perturbed by instrumentation. Use a serial capture host, camera, network probe, managed power controller, or hardware signal. Define service readiness as a correct application response, not merely an open socket.

Correlate external and internal timelines with a marker visible to both, such as a loader serial line and userspace message sent to the same host. Do not subtract clocks with unrelated origins.

## 26. Statistics

Report sample count, median, p95 or range, and start condition. One ninety-second timeout among twenty five-second boots matters despite an acceptable mean. Separate cold, warm, and resume paths.

Randomize A/B order so temperature, caches, and network state do not favor one version. Bimodal timing often reveals a timeout or race; explain the distribution instead of publishing one fast run.

## 27. Correctness cost table

Every optimization removes or moves a guarantee. Disabling fsck removes validation. Shorter timeouts abandon slow devices. Smaller host-only initramfs reduces migration support. Disabling Secure Boot removes authentication. Removing network-online changes readiness ordering. More parallel units can expose missing dependencies.

Sometimes the trade is correct. Write it down, assign ownership, and test failure behavior. After optimizing an optional mount, disconnect it. After changing loader updates, interrupt one in a VM. A faster normal path with broken recovery is a regression.

## 28. Report template

Record the question and endpoint; hardware or VM; firmware; loader entry; kernel, command line and initramfs; userspace target; cold/warm condition; measurement method; clocks; trace configuration; run count; distribution of times; first constraining boundary; single change; correctness tests; and raw artifact locations.

This lets another engineer reproduce the result and identify instrumentation overhead.

## 29. Privacy

Boot logs expose serials, UUIDs, network addresses, command lines, crash addresses, usernames, and device topology. Traces expose filenames and process activity. Store raw evidence under incident controls and redact copies, not originals.

Lowering kptr restrictions or lockdown for profiling changes security. Use isolated labs and restore policy. Observability itself is an attack surface; choose the narrowest tool that answers the question.

## 30. Firmware-versus-userspace case study

A laptop takes forty seconds from power button to login. systemd-analyze reports three seconds of userspace and two seconds of kernel time. The missing interval is not an invisible slow service; it precedes the kernel.

External video shows thirty seconds before the boot-loader menu. Firmware serial or setup diagnostics reveal repeated network boot and a timeout on an absent storage device. Removing an obsolete boot option reduces the interval while kernel and userspace numbers remain unchanged.

The case demonstrates why the measurement boundary matters. Optimizing unit parallelism could at best improve the already small userspace interval. Conversely, if firmware time is one second and userspace critical chain is thirty, changing UEFI Fast Boot cannot solve the real delay.

## 31. Instrumentation overhead experiment

Boot the same VM with normal logging, loglevel 7 on a fast virtual console, and loglevel 7 on a deliberately slow serial console. Record total and kernel time. The message-generating workload is similar in the latter two, but output device cost differs.

Next enable initcall_debug and then a narrowly filtered trace. Quantify overhead. This calibrates the observer: a five-second driver init under verbose serial logging may not take five seconds without printing.

Do not "correct" every timestamp mathematically. Use instrumentation to locate a mechanism, then confirm with a lighter measurement.

## 32. Review questions

Which clock timestamps the earliest line? Can the selected console block? Where are records stored before /var is mounted? Does a socket-ready endpoint equal application-ready? Which units are on the critical path rather than simply slow? Did any trace events drop? Is the previous boot journal persistent? Can pstore survive the observed reset type?

Answers define the confidence of the conclusion. A performance report without these boundaries is a screenshot, not an experiment.

Archive the raw artifacts and a small machine-readable metadata file together. Future kernel or firmware changes may offer better parsers, and reanalysis is possible only when original timestamps, trace records, build IDs, and environment survive. Derived charts are convenient; raw evidence is the durable scientific result.

Give every capture a boot ID and experiment ID. File names like dmesg-final-new obscure provenance; structured identifiers prevent accidental comparison of unrelated runs.

Keep the experiment notebook beside the artifacts. Human memory quickly merges similar reboots, especially when several differ by only one command-line parameter.
